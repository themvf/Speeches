## Polymarket Earnings Sharp-Trader Tracker (JIRA Epic SEC-24, 2026-07-14)

Goal: identify consistently-sharp traders in Polymarket's per-company "Will X beat quarterly earnings?" markets and surface their live positioning against the week's earnings calendar. **Pilot (SEC-25), the "Prediction Markets" tab (SEC-28), AND the live pipeline (SEC-26 ingestion + SEC-27 scoring) are implemented; SEC-29 (sharp-entry alerts) is plan only. Production activation still needs the one-time `backfill=true` dispatch of `polymarket-earnings-sync.yml` (see below).**

**Live pipeline (SEC-26/27, 2026-07-15).** `polymarket_earnings_sync.py` + `.github/workflows/polymarket-earnings-sync.yml` running **3x daily at 9:00am / 4:25pm / 9:00pm ET** (user-specified; crons pinned to EDT 13:00/20:25/01:00 UTC since GitHub cron is UTC-only — +1h winter drift is harmless because ingestion is cursor-based and therefore complete at any cadence). Per run: refresh open earnings markets (gamma), detect resolutions (closed events, endDate-desc), ingest new fills per unsettled market (client-side cursor: newest-first paging stopped at the stored max fill timestamp — the data API has no since-param and **no trade ids**, so dedup is a content-hash `fill_key` with ON CONFLICT DO NOTHING), settle newly-resolved markets into the durable `polymarket_wallet_market_results`, recompute `polymarket_wallet_stats`+archetypes from that durable table (never raw fills), then prune. **Retention is settle-then-prune keyed on settlement date, never fill age** (fills deletable 7 days AFTER their market settles; age-based pruning would have corrupted settlement for markets open >30 days — caught in plan review). Cold start: `--backfill` settles ~120 resolved markets in memory straight into the durable table (their raw fills never stored). Schema in `neon_feeds._ensure_polymarket_schema()` (4 tables: markets/trades ephemeral-ish, results/stats durable). `GET /api/market/predictions` is now **force-dynamic live-first**: reads the Neon tables (consensus positions computed from our own ingested tapes via one SQL aggregate — replaces the pilot's 40-60 per-wallet API calls and its last-500-fills blind spot) and **falls back to the committed static snapshot with a visible warning whenever tables are missing/empty or the DB is unreachable** (`isLive` boolean tells the UI which source served). Tests: `tests/test_polymarket_sync.py` (cursor stop/boundary, fill_key dedup determinism, durable-stats recompute + archetype gate, and a mock-ordering test asserting settle-before-prune and never-settle-open). **To activate in production: push (workflows deploy automatically), then dispatch `polymarket-earnings-sync.yml` once with `backfill=true`; until then the tab keeps serving the snapshot.**

**Prediction Markets tab (SEC-28, 2026-07-15) — static-snapshot-first, same pattern as the CBOE tab (SEC-19).** `build_prediction_snapshot.py` bakes `apps/web/lib/server/prediction-markets-data.json` from the pilot analysis (reuses `polymarket_pilot.py`'s now-refactored `analyze_resolved_markets`/`rank_wallets`/`classify_archetype`); `GET /api/market/predictions` serves it `force-static` (zero DB/network, `isLive:false` + warning banner). Two views in `prediction-markets-tab.tsx`: **Calendar** (open earnings markets with Polymarket implied-beat % + a sharp-money consensus cell — counts `early_sharp`+`longshot` wallets only, `news_scalper` positions shown per-wallet but never aggregated) and **Sharp wallets** (leaderboard filterable by archetype, drawer with why-badge reasoning + open positions + Polymarket profile link). Archetype thresholds are code constants in `classify_archetype` (≥8 markets gate; early_sharp = entry ≤60¢/win ≥55%; news_scalper = entry ≥80¢/win ≥90%; longshot = entry ≤35¢/win <40%/ROI >1) — unit-tested in `tests/test_polymarket_pilot.py`. To refresh the snapshot: rerun `python build_prediction_snapshot.py` and commit the JSON. The live pipeline (SEC-26/27) swaps the route's data source behind this exact contract with no UI change. Regenerating verified in a snapshot with e.g. TSM at 91% implied beat but 3 tracked early sharps (incl. `mmmbop`) all holding No — the "sharp money disagrees with the crowd" signal.

Key verified facts (2026-07-14, all live-probed — do not re-guess):
- **Kalshi was evaluated first and rejected for this use case**: its public trades endpoint (docs.kalshi.com) returns zero identity fields — CFTC-regulated anonymous tape, no API tier changes that. A "sharp flow footprint" detector (anonymous pre-jump accumulation patterns) remains viable on Kalshi if ever wanted, but trader-following is impossible there.
- **Polymarket exposes full per-trade identity publicly, no auth**: `data-api.polymarket.com/trades` carries `proxyWallet` + pseudonym per fill; queryable by `market=<conditionId>` and by `user=<wallet>`. Use `takerOnly=false` (default `true` returns taker fills only — ~3x fewer rows, and maker-side position reconstruction is impossible without it). **The endpoint 400s past offset ~3500**, so mega-markets yield only their most recent ~3.5k fills (newest-first) — handle as partial tape, don't discard the market (the pilot's one rerun-worthy bug).
- **Earnings markets mirror the user's earnings-calendar app exactly** (same tickers/dates/EPS thresholds): `gamma-api.polymarket.com/events?tag_slug=earnings`. 100+ resolved events on the first volume-ordered page (NVDA ~$995k), median closed-event volume ~$60k → small, cheap data.
- **Pilot answer: yes, persistent skill differentiation exists.** 120 resolved markets / 153k fills / 19.3k wallets → 1,704 with ≥5 markets. P&L method: reconstruct per-wallet per-market net position + cash from fills, settle winners at $1 (negative nets clamped — split/merge fills aren't in the tape). The `avg_winner_entry_price` metric cleanly separates archetypes: early-conviction sharps (buy eventual winners at 13-55¢: `mmmbop` $20.7k PnL/65 mkts/entry 0.55; `KingDingaLing888` ROI 2.60/entry 0.13), near-certainty scalpers (entry 0.85-0.98, win% 98-100 but ROI 0.03-0.35 — incl. a wallet literally named `PRNewswire`, $14.5k at 100% win rate: news-latency trading), and longshot specialists (win% ~27 but ROI 1.38+). Pilot also fetched top-10 wallets' current open-earnings positions and found `YoungAlphaGoat` (65% win, $12.5k) live-holding No on UNH (reports 2026-07-16, on the user's calendar) — the exact "follow them into related markets" deliverable.
- Pilot caveats for the production build (SEC-26/27): per-wallet open-position check scans only the wallet's most recent 500 fills; deep tape of mega-markets truncated (above); P&L ignores on-chain splits/merges.
- **Retention design (user requirement, 2026-07-15) — durable sharp-wallet DB, ephemeral raw fills.** SEC-26/27 success criteria now mandate a split: raw fills (`polymarket_trades`) are 30-day-pruned, but the sharp-user record is durable and accumulates. Hard ordering: a market's fills may only be pruned AFTER it resolves and is settled into a durable `polymarket_wallet_market_results` table (one compact row per wallet-per-market: side/pnl/correct); `polymarket_wallet_stats` + the watchlist are (re)computed from THAT table, never from raw fills — so a wallet's full multi-quarter track record survives indefinitely and pruning is invisible to the product. Same durable-rollup-vs-ephemeral-detail pattern as `daily_stock_attention` (durable) vs `reddit_attention_items` (90-day pruned). **Cadence: once-daily cursor-based ingestion** (store newest-seen fill ts per market, fetch only since); because fills are immutable+timestamped, cadence affects only display freshness, never completeness. Optional report-day intraday bump is SEC-29 (alerts) territory, gated to imminent-report windows only.

## Recap Architecture Review - July 2026

Use this note when debugging recap generation failures, stale/duplicated topic rows, or recap-related rate-limit errors. A review of the Daily Recap stack (`apps/web/app/api/intel/recap/{generate,settings}/route.ts`, `apps/web/app/api/intel/recap/route.ts`, `apps/web/app/recap/page.tsx`, `apps/web/components/recap-dashboard.tsx`, and the `daily_recaps`/`recap_settings` tables in `neon.ts`) found the items below. Status: **items 2-4 and the small correctness fixes are implemented; items 1 and 5 are deliberately deferred as separate feature work.**

### What was implemented

- **Positional cursor replaced with topic_key — DONE.** `/api/intel/recap/generate` used to take `{ date, cursor, batchSize }` and re-slice `selectedRules` server-side on every request; if settings or active rules changed mid-run, topics could be silently skipped or double-generated, and a failed request had no clean retry semantics. Now takes `{ date, topicKey }` — one topic per request, keyed by identity rather than position, so a request is naturally idempotent and safely retryable. Response is `{ status: "generated" | "skipped" | "failed", ... }` per topic instead of an aggregate cursor/done/remaining envelope. `recap-dashboard.tsx`'s `generate()` now loops over the client's own `selectedKeys` set directly instead of following a server-returned cursor.
- **Redundant per-topic work removed — DONE.** With N topics selected, the old code re-fetched the same 400 articles and re-ran `matchItemsToTopics` against *all* N rules on every one of the N requests, then discarded every rule's matches except the one it needed that call. Also called `deleteBlockedRssArticles` once per topic request — a full sweep already run by `rss-refresh`, `feed/route.ts` (twice), and `rss-analysis-runner.ts` on every relevant path, and specifically flagged as expensive in the Database Cost Audit above. New `matchItemsToTopic()` scores only the requested rule (confirmed via `getTopicMatches`'s implementation that per-rule scoring has no cross-rule dependency, so this is a pure subset of the old computation, not a behavior change); the `deleteBlockedRssArticles` call was removed from the recap route entirely.
- **Fallback rows are now labeled — DONE.** When the model call fails/times out/returns an invalid response, `generateTopicSummary` falls back to a templated `buildSourceFallbackSummary()` string that was previously stored in `daily_recaps` indistinguishable from a real LLM summary (only a transient `console.warn`). Added a `fallback BOOLEAN NOT NULL DEFAULT false` column (idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, same pattern as the existing `sources` column migration), threaded through `saveRecapRows`/`getTodaysRecap`/`DailyRecapRow`, and a small "Fallback" badge on `RecapCard` in the dashboard.
- **Timeout math fixed — DONE.** The route budget is `maxDuration = 60`; with the old `MODEL_REQUEST_TIMEOUT_MS = 35_000` and (now-enabled) 2 attempts, worst case was 70s — over budget, so a slow second attempt would die as an opaque non-JSON 504 instead of falling back cleanly. Lowered to `22_000`ms (2 attempts = 44s, leaving headroom for the DB reads/matching that now happen only once per request instead of N times).
- **Retry loop re-enabled — DONE.** `MAX_MODEL_ATTEMPTS` was `1`, making the existing "previous response was incomplete, regenerate" second-attempt prompt unreachable dead code. Now `2` — validation failures (the most common reason to retry: incomplete JSON, missing Key Points, mid-sentence cutoff) get one real retry before falling back, at no extra risk now that the timeout math above leaves room for it.
- **Prompt/content count mismatch fixed — DONE.** The prompt said "Summarize the following `{items.length}` sources" but only fed the model the first `MAX_ITEMS_PER_TOPIC` (20) — so a 60-item topic told the model to summarize 60 while showing it 20. Now uses the sliced count.
- **Truncation and settings-drift visibility — DONE.** If `getRecentArticles({ limit: 400 })` returns exactly 400 (the window may have more), the response now carries a `warnings` array entry surfaced in the dashboard, matching the `warnings`-array convention `/api/metrics` already uses elsewhere in this app instead of failing silently.
- **429 handling in the client loop — DONE.** A rate-limit response used to abort the whole multi-topic generation run, abandoning every topic after it. The dashboard now retries the same topic with backoff (up to 3 attempts, 1.5s/3s/4.5s) instead of aborting the run.

### Deliberately not done in this pass (separate feature work)

- **Scheduling.** Recap is currently a pull product — a recap only exists for a date if someone visited the page and clicked Generate. The storage layer (`daily_recaps` keyed by `(recap_date, topic_key)`) is already shaped for pre-generation; a daily scheduled trigger (a workflow curling the endpoint per selected topic with `CRON_SECRET`, matching the `checkCronAuth` pattern already used elsewhere) would make the page always-warm. Not implemented — this is new scheduling infrastructure, not a fix to existing code.
- **Real corpus-document integration.** `RecapItem`'s `matchText`/`speaker`/`source_type: "document"` fields already imply enrichment-tag-matched corpus documents, but no such source exists today — "documents" are just RSS articles from official feeds relabeled by feed-key prefix (`isOfficialRegulatoryFeed`), so e.g. SEC speeches only appear in a recap if the RSS feed happens to carry them. Now that the Neon `documents` mirror (roadmap item 4, Phase 3) is populated, matching enriched documents published in the recap window via their tags/keywords is an indexed query away — building that is real feature work, not a bug fix, and is left as a follow-up.
- **Per-user settings.** `recap_settings` is a single global row (`LIMIT 1`). Fine today; worth revisiting if recap ever goes per-user given Clerk is already wired into the app.

### Verification

`tsc --noEmit`, `eslint --max-warnings 0`, and `next build` all pass. No live `DATABASE_URL` in this sandboxed session, so the full generate flow couldn't be exercised against real recap data — instead verified via a local dev server (no DB) that: the page still renders through the existing `Promise.allSettled` fail-soft pattern, the new client-side "no topics selected" guard fires without making a network call, `POST /api/intel/recap/generate` returns a clean `{"ok":false,"error":"topicKey is required."}` for a missing `topicKey` and a clean DB-unavailable error (not a crash/500 HTML page) once past validation. A live-DB smoke test of a full generate run is still worth doing after deploy.

## Database Cost Audit (Neon/GCS) - July 2026

Use this note when debugging Neon compute-time spend, query latency on `rss_articles`/`intelligence_mentions`, or unbounded storage growth. An audit of Neon and GCS costs found several architectural drivers, all in `apps/web/lib/server/neon.ts`. Status: **all four proposed Neon fixes below are implemented.** The GCS-side findings (bucket versioning/lifecycle status, and whether the ~23 scheduled workflows' full-blob rewrites should be reduced) were **not implemented** — they require direct GCS console verification and/or the already-scoped Neon `documents` migration (see Ingestion Pipeline Review below), not a quick code change.

### Neon findings and fixes

- **`ensureSchema()` ran unmemoized on nearly every call** — ~24 DDL/migration statements, called from ~16 places inside `neon.ts` itself with no caching, meaning a single request (e.g. one 10-minute rss-refresh cron tick) could re-run the full check 6-10+ times, and every real page load touching feeds/articles/topic-rules paid the same cost. **Fixed**: `ensureSchema()` now caches the in-flight/completed promise in a module-level `_schemaEnsured` (cleared on failure so the next call retries instead of wedging permanently), so the DDL block runs once per process lifetime instead of once per query.
- **`saveIntelligenceMentions` did one DELETE + one round-trip INSERT per mention** — called once per analyzed RSS article with up to ~90 potential mentions (keywords + individuals + entities + topics combined), each a separate network round trip to Neon's HTTP driver. **Fixed**: extracted a pure `prepareMentionBatch()` helper that dedupes by `(mention_type, normalized_value)` — the only possible collision given the table's unique constraint — keeping the last occurrence (matching the old loop's overwrite-on-conflict semantics), then a single `INSERT ... SELECT ... FROM unnest(...)` multi-row statement replaces the per-mention loop. One save call is now ~2 round trips (delete + insert) instead of up to ~91.
- **Age-based retention is available but opt-in** — `pruneOldRssData(retentionDays)` deletes `rss_articles` older than the configured window (`rss_article_analysis` cascades via its FK; `intelligence_mentions` needs an explicit sweep since it is keyed generically by `source_type`/`source_id` with no FK). `/api/intel/rss-refresh` runs it only at 03:00 UTC and only when `RSS_ARTICLE_RETENTION_DAYS` is explicitly set to a positive value. With the variable unset or `0`, historical RSS data is preserved.
- **Three cleanup queries did full-table scans on every call, against an ever-growing, unpruned table** — `deleteInvalidCouponArticles` (15 leading-wildcard `ILIKE '%word%'` conditions), `deleteNonEnglishPrNewswireArticles`, and `deleteBlockedRssArticles` (regex `~*` conditions `OR`-combined with a `feed_key LIKE` clause, which defeats index-only planning for the whole query) — none of these can use a standard index, and they're called far more often than just the 10-minute cron: also from `rss-analysis-runner.ts`, `/api/intel/feed` (twice, on every feed page load), and `/api/intel/recap/generate`. **Fixed**: all three now filter on `fetched_at >= now() - INTERVAL 'N hours'` first (default 14-day window, configurable per-call), using the existing `rss_articles_fetched_at` index to turn an O(N) sequential scan into a bounded index range scan. Trade-off: if a topic rule is edited, `deleteBlockedRssArticles` will only retroactively reclassify articles fetched within that window, not the full history — acceptable given the new retention policy above will eventually prune anything older anyway.

**Verification**: `tsc --noEmit`, `eslint --max-warnings 0`, and `next build` all pass. No `DATABASE_URL`/live Neon access exists in this sandboxed session, and there's no existing TS-side DB-mocking harness in this repo (unlike the Python side's mocked-psycopg2 pattern) — and `@neondatabase/serverless`'s `neon()` client only speaks Neon's proprietary SQL-over-HTTP protocol, so it can't be pointed at a generic local Postgres either. Docker Desktop wasn't running and didn't come up after ~5 minutes of waiting (likely needs one-time interactive WSL2 setup), so instead the exact SQL from every changed function was executed against `@electric-sql/pglite` (real Postgres compiled to WASM, in-process, no daemon needed) with the same schema from `ensureSchema()`. Verified: the batched `unnest` multi-row insert (including re-save/upsert semantics and an empty-batch no-op), all three windowed cleanup queries (confirmed a 1-day window excludes and a 30-day window includes the same 20-day-old matching row), and `pruneOldRssData` (confirmed the FK cascade into `rss_article_analysis`, the explicit `intelligence_mentions` sweep, and that recent unrelated rows survive) — all behaved exactly as intended. Also confirmed, as a negative control, that skipping the in-app `prepareMentionBatch()` dedup step and sending a raw colliding batch straight to the same SQL throws Postgres's real `ON CONFLICT DO UPDATE command cannot affect row a second time` error, proving the dedup step is load-bearing rather than defensive-only. This validates the SQL and application logic thoroughly; the one thing it does not cover is the Neon-specific HTTP driver's own parameter/array serialization, which should still get a quick real-Neon smoke test after deploy.

### GCS findings — not implemented, need direct verification or the Neon migration

- ~23 scheduled workflows read-modify-write the full `custom_documents.json` blob (36+ MB and growing) at frequencies from hourly to every 3 hours; likely 300+ full download/upload cycles/day, which is probably the single largest cost line item (egress, not storage). Reducing this requires either fewer/less-frequent full-blob rewrites or cutting readers over to the already-scoped-but-dormant Neon `documents` table (see Ingestion Pipeline Review's Neon migration Phase 2/3).
- GCS bucket-level Object Versioning/lifecycle rules are not set in application code (`gcs_storage.py`, `gcs-loader.ts`) — verify directly in the GCS console. If versioning is on, every one of those 300+ daily rewrites of a 30-40 MB object retains a full old copy forever, which could silently dominate the bill. This is the single highest-priority manual check, independent of any code change.

### Critical findings

- **A transient GCS read failure can silently roll back or wipe the corpus.** Both `_load_json_store` (`run_financial_news_pipeline.py`) and `POST /api/admin/documents` (`apps/web/app/api/admin/documents/route.ts`) treated a failed remote read the same as "no data exists," then saved that empty/stale payload back over the real corpus in `custom_documents.json`. `--require-remote-persistence` only guarded writes, not reads. **Fixed**: `_load_json_store`/`_save_json_store` now track per-blob whether the remote read errored (`_REMOTE_LOAD_ERRORED_BLOBS`) and refuse to save under `require_remote_persistence` if so; `app.py`'s independent duplicate of this load/save logic got the same guard (`_CUSTOM_DOCS_REMOTE_LOAD_ERRORED`). `gcs-loader.ts` gained `downloadGcsJsonSafe`, which distinguishes not-found from error; both admin document routes (`POST`/`DELETE`) now return 503 on a read error instead of proceeding.
- **All YouTube videos collapse to one dedup key.** `_url_match_key` (`run_financial_news_pipeline.py`, and a duplicate copy in `app.py`) stripped query strings, so every `youtube.com/watch?v=<id>` URL normalized to the same key — each new video ingested overwrote the previous one in `custom_documents.json`. Also collapsed `http://` vs `https://` variants of any URL. **Fixed**: scheme is normalized to `https`, the query string is preserved (sorted, for stable ordering) except for known tracking params (`utm_*`, `fbclid`, `gclid` — stripped so RSS re-fetches with different tracking tags still dedupe, matching the convention already used in `trade_media_scraper.py`). Both `app.py` and `run_financial_news_pipeline.py` were updated identically since they must compute the same doc-identity keys. Note: the local committed `data/custom_documents.json` had zero YouTube records at fix time (predates the connector), so no backfill was needed there — the real corpus lives in GCS and wasn't independently audited.
- **Lost-update races between concurrent workflows writing the same JSON blob.** ~15 scheduled GitHub Actions workflows plus Vercel admin routes all do unguarded read-modify-write of `custom_documents.json` / `document_enrichment_state.json` / `rule_summaries.json` with only per-workflow concurrency groups. **Partially fixed**: the Python side (`_load_json_store`/`_save_json_store`) now tracks the GCS object `generation` observed at load (`_BLOB_GENERATIONS`) and passes it as an `if_generation_match` precondition on save, raising a clear `RuntimeError` on conflict instead of silently overwriting a concurrent writer's changes (chained correctly across enrichment's checkpointed saves). This is fail-loud, not retry-and-reapply — a conflict fails the run rather than auto-merging, which is judged safer than reapplying arbitrary in-flight mutations. The Vercel admin routes (`apps/web/app/api/admin/documents/*`) still lack this guard — see spawned follow-up task for extending `downloadGcsJsonSafe`/`uploadGcsJson` with the same generation-match pattern (couldn't be verified against a live GCS bucket in the original session). Longer-term, migrate documents to normalized Neon storage instead of one JSON blob.

### What broke

- `apps/web/lib/server/neon.ts` now seeds default RSS feeds with `ON CONFLICT (feed_key)` and updates `feed_url`, preventing duplicate `rss_feeds_feed_key_key` errors during `ensureSchema()`.

## Stock-Specific News Connectors

Use this guidance when adding connectors that support stock/ticker-specific news, market commentary, or "stocks getting attention" workflows.

### Feasibility By Source

- RSS, blogs, newsletters: high feasibility. Prefer RSS/Atom feeds and normal article extraction. This matches the existing `trade_media_scraper.py`, `wsj_rss_scraper.py`, and `substack_public_scraper.py` patterns.
- Public Substack posts: high feasibility for public posts. Prefer publication `/feed` URLs and public post extraction. Do not attempt to bypass paid/private posts; mark them as access-limited and preserve metadata/preview only when available.
- Reddit: medium feasibility. Prefer OAuth/PRAW for reliable access. The existing `reddit_scraper.py` supports this shape. Treat commercial use as requiring Reddit API compliance review/permission, and expect unauthenticated JSON access to fail from cloud IPs.
- X/Twitter: medium feasibility but potentially costly. Use official X API v2 for recent search, user timelines, and streams. Do not scrape X pages. Add strict budget caps, source allowlists, and rate-limit handling before enabling production jobs.
- YouTube: medium feasibility. Use the YouTube Data API for channel/video discovery, metadata, comments, and stats. Treat transcripts/captions as conditional on availability and authorization.
- Telegram: medium/low feasibility. Bot API works for channels where the bot is authorized and receives channel posts. Do not assume arbitrary public-channel history can be ingested reliably.
- TradingView: low feasibility for ingestion. TradingView widgets are display tools, not a market-data export API. For prices, candles, fundamentals, or indicators, use licensed market-data providers instead.

### Preferred Architecture

Build stock-news ingestion as connector modules feeding a normalized schema, not as a single scraper.

Core records should include:

- `sources`: platform, handle/url, source owner, access mode, priority, compliance status.
- `raw_items`: platform id, source id, author, published timestamp, canonical URL, raw text/metadata, engagement metrics, fetched timestamp.
- `mentions`: raw item id, ticker/entity, confidence, context snippet.
- `daily_stock_attention`: ticker, mention count, weighted score, mood, source count, top source ids.
- `analyst_profiles`: curated identity, handles, channels, notes, credibility metadata.
- `daily_briefs`: generated summaries with source citations.

Pipeline order:

1. Ingest new posts/articles from each connector.
2. Normalize records into one internal schema.
3. Deduplicate by platform id, canonical URL, and content hash.
4. Extract tickers, cashtags, companies, sectors, and themes.
5. Classify mood as bullish, bearish, mixed, neutral, or informational.
6. Aggregate "stocks getting attention" using mention count, source diversity, source weight, freshness decay, and engagement.
7. Generate source-backed daily briefs with links/citations to originals.
8. Label output as research context only, not investment advice.

### Implementation Order

Start with sources that are legally and operationally stable:

1. Expand RSS/blog/Substack connectors.
2. Add Reddit OAuth/PRAW configuration and commercial-use checks.
3. Add X API connector with explicit budget controls and curated handles.
4. Add ticker/entity extraction and mood aggregation.
5. Add daily brief generation and source-backed UI surfaces.

Avoid starting with Telegram history or TradingView data ingestion. Those should only be added after the reliable source pipeline is working and the access model is clear.

### Compliance Defaults

- Prefer official APIs and public RSS feeds over page scraping.
- Preserve canonical URLs and source attribution for every item.
- Do not bypass paywalls, login walls, CAPTCHAs, private groups, or anti-bot controls.
- Store enough raw metadata to audit why a ticker appeared in a summary.
- Separate source-backed facts from model-generated summaries.
- Add per-connector rate limits, retries, and failure reporting before production scheduling.
